# Architecture

Tick is a to-do app for one person or a few people (a household, a small team), running on Cloudflare. Every account has its own tasks, places, keys, devices and settings; one installation, one database. This document describes how it is built. Setup steps are in [SETUP.md](SETUP.md).

## Settings
After the install, you change settings in the app (⚙ Settings in the sidebar). `wrangler.jsonc` (your own copy of `wrangler.example.jsonc`, not in git) and secrets hold the starting values and what only belongs to the install.

**Per person** (in D1 `user_settings`, one row per user and key, so all devices of that person and the server share it). Precedence: a row in `user_settings` → the config → the built-in default. The config is therefore the starting value for everyone; what a person chooses in the app wins for that person, and a deleted row makes the config count again. An invalid value in a row is ignored.

| Setting | `user_settings` key | Config fallback | Built-in |
|---|---|---|---|
| Time zone (IANA; the server refuses an unknown zone with a 400) | `timezone` | `TIMEZONE` | `UTC` |
| Time for a reminder without a time | `reminder_time` | | `09:00` |
| Daily reminder for overdue tasks (`HH:MM`, or `off`) | `overdue_time` | | `09:00` |
| Week starts on | `week_start` (`mon`, `sun`) | | Monday |
| Fallback webhook (`https://` only; an empty row = off, also when the secret is set) | `fallback_webhook` | `FALLBACK_WEBHOOK`, **only for the administrator** | none |

**Per installation** (in D1 `settings`). Precedence: a row in `settings` → the config → the built-in default. Only the administrator can change it; a member gets a 403 (`err.admin_only`).

| Setting | `settings` key | Config fallback | Built-in |
|---|---|---|---|
| Default language: fallback webhook, subscriptions without a language, last resort of "Automatic" | `default_locale` | `LOCALE` | `en` |

Changing the time zone in the app keeps the wall-clock time: that person's open tasks get the same local date and time in the new zone for `remind_at`, `repeat_start` and `repeat_at` (written in one batch; `repeat_prev` is cleared). Completed tasks and other people's tasks are not touched.

**Per device** (in the browser, so not shared): theme (`tick.theme`: automatic, light, dark), colour theme (`tick.palette`: default or `retro`, independent of light/dark; a new theme is one light and one dark block in `public/style.css`), text size (`tick.font`: `s`, `m`, `l`, `xl`), spacing between tasks (`tick.density`: compact, normal, roomy) and language (`tick.lang`, also in the cookie `tick_lang`). `public/theme.js` sits in `<head>` (also on the login page) and puts them on `<html>` as data attributes before the first paint, so nothing flashes. The background photo (optional, needs `FILES`) is per person, not per device: one image in R2 under `bg/<userId>`, its version in `user_settings` (`background`, also in `GET /api/settings`); `PUT`/`GET`/`DELETE /api/background` (session only, `src/background.ts`). The device remembers the version in `tick.bg` and `theme.js` sets `data-bg` and `--bg-image`; another device picks it up when Settings is opened. Deleting the account removes the object. Notifications also belong to a browser (a push subscription).

**Only in the config** (install-level, not in the app): `ADMIN_CONTACT` (`mailto:` contact for push services and Nominatim), `VAPID_PUBLIC_KEY` (var), `VAPID_PRIVATE_KEY` and `SESSION_SECRET` (secrets), `ANDROID_PACKAGE` (var, optional: applicationId of your own Android build, so the PWA can wake it after a location change), `ANDROID_CERT_SHA256` (var, optional: SHA-256 fingerprint(s) of your signing key, comma-separated; with `ANDROID_PACKAGE` it makes `/.well-known/assetlinks.json` link the app to this domain), `DEV_AUTH_BYPASS`.

**Still read from the config, now optional:** `LOGIN_PASSWORD` (only for the administrator: until a password is set in the app, and for the emergency route), `API_TOKEN` and `INBOX_TOKEN` (old keys that keep working until you switch them off in the app).

`loadInstallPrefs` (`src/prefs.ts`) reads `settings` with one query per request, before the login check (`c.get('install')`: the default language and the switches for the old secrets). After the login check, `loadUserPrefs` reads that person's `user_settings` with one more query, and `c.get('prefs')` holds both. The cron reads `loadInstallPrefs` once per run and, per user with due reminders, `getUser` and `loadUserPrefs` once (kept in a `Map` for the run). The PWA gets the values from `/config.js`, a module the Worker generates with the settings of the logged-in user: `locale` (the language of this device), `defaultLocale`, `timeZone`, `reminderTime`, `weekStart`, `androidPackage`, `userId`, `userName` and `isAdmin`. `public/settings.js` imports it first, so language and time zone are set before the other modules load. The service worker caches it with the shell, so offline use keeps the right language and zone; another device picks up a change on its next start.

## Data model (D1)
- `tasks`: id, `user_id` (the owner; `push_subscriptions`, `api_keys` and `pair_codes` have a `user_id` too, default the admin's id), title (max. 500 characters), description (max. 10,000, markdown), list (max. 100 characters: `POST`/`PATCH /api/tasks` refuse more with a 400, `POST /api/inbox` truncates so an automated task is never lost), parent_id (one level of subtasks; a subtask follows the list and completion of its parent), position (fractional index, low = on top; the server redistributes a group as soon as two neighbours are less than 1e-6 apart), `pinned` (0/1, only on top-level tasks: a pinned task comes before the others in every list, each part in its own `position` order; becoming a subtask clears it), remind_at (UTC), notified, `repeat_rule`, `repeat_start`, `repeat_at`, `repeat_prev` (see "Repeating reminders"), done, done_at, source (`app` | `api` | `import`), `copy_group` (see "Copy groups"), created_at, updated_at.
- Place on the task: `loc_name` (max. 100 characters), `loc_lat`, `loc_lng`, `loc_radius` (whole number, 200 to 2000 m; without one: 200 m when leaving, 500 m on arrival), `loc_trigger` (`enter` | `exit`) and `loc_notified` (already notified, like `notified`; the owner's, see `task_shares`). The five place fields are set or empty together; every change resets `loc_notified` to 0, also in every share row of the task.
- `places`: favourite places (id, `user_id`, name unique per account and case-insensitive (`UNIQUE (user_id, name)`), lat, lng, radius, created_at, updated_at). A favourite is a template: a task gets a copy, so editing or deleting it does not move existing tasks. The trigger belongs to the task.
- `push_subscriptions`: endpoint, p256dh, auth, user_agent, created_at, `user_id` (a reminder only goes to the subscriptions of the task's owner), `locale` (`en` | `nl`; the PWA sends its language when subscribing and on every language change, and every notification goes out in the language of its subscription. No value means the default language).
- `api_keys`: keys made in the app: id, name, kind (`full` | `inbox`), `hash` (SHA-256 hex of the key; the key itself is never stored), `hint` (last 4 characters, to recognise it), created_at, last_used_at (updated at most once an hour).
- `pair_codes`: one-time codes for linking the Android app: id, `hash` (SHA-256 hex of the code; the code itself is never stored), expires_at (2 minutes after creating), used_at. Expired and used rows are removed when the next code is requested.
- `devices`: what an Android phone reports about itself, one row per key (`key_id` is the `api_keys` id, or `env-api` for the old `API_TOKEN`): name, notifications (0/1), location (`always` | `foreground` | `off`), app_version, seen_at. Deleting a key deletes its row.
- `users`: id, name, `email` (unique, case-insensitive, may be empty), `password_hash`, `role` (`admin` | `member`), `session_version`, created_at, last_seen. The migration makes one admin with the fixed id `00000000-0000-4000-8000-000000000001` (name `Tick`, no email) from the old `settings` rows `password_hash` and `session_version`; a fresh install has the same row.
- `user_settings`: user_id, key, value; the per-person settings `timezone`, `reminder_time`, `week_start` and `fallback_webhook`. The migration copies them from `settings` for the admin; the old rows stay in `settings` but are no longer read (so an older Worker still works between `db:migrate` and `deploy`, or after a rollback). A later migration will remove them.
- `account_links`: invitation and reset links: id, `hash` (SHA-256 hex of the code; the code itself is never stored), `kind` (`invite` | `reset`), user_id, created_by, expires_at, used_at.
- `settings`: key, value; only what belongs to the whole installation. Keys: `default_locale`, `env_api_token_off` and `env_inbox_token_off` (the switches for the old secrets), `env_api_token_used` and `env_inbox_token_used` (when they were last used). Old rows `password_hash`, `session_version` (now in `users`) and `timezone`, `reminder_time`, `week_start`, `fallback_webhook` (now in `user_settings`) may still be there; the code no longer reads them, and a later migration will remove them.

- `tasks.deleted_at`: the trash (ISO UTC, `NULL` = not deleted). Deleting sets it on the task and its subtasks with the same timestamp, so restoring brings them back together. Every query outside the trash routes filters `deleted_at IS NULL`.
- `task_shares`: one row per invitation or participation, always on a top-level task: id, `task_id` (`ON DELETE CASCADE`), `from_user` (the owner), `to_user`, `mode` (`shared` | `copy`), `status` (`pending` | `accepted`; only `shared` is ever accepted, a copy row disappears on accepting), `list`, `position` and `pinned` (the recipient's own list, order and pin), `loc_notified` (whether the recipient's phone already notified the place, migration `0015`; so the first person to arrive does not use up the notification for the others. Subtasks keep the shared `tasks.loc_notified`), created_at, responded_at. `UNIQUE (task_id, to_user)`.
- `reminder_sent`: task_id, user_id, `remind_at`: per person, for which reminder time they already got a notification. A new `remind_at` counts as not notified by itself.
- `attachments`: id, `task_id`, `user_id` (who uploaded it), `name` (max. 200 characters, without a path), `mime`, `size`, `r2_key` (`a/<uuid>`), `width`/`height` (images, from the client), `status` (`pending` during the upload, then `ready`), created_at. No foreign key: the R2 object has to go too, and that cannot happen in a D1 batch. Deleting a task for good (or an account) leaves its rows behind; the cron (`sweepAttachments`) removes rows whose task is gone and uploads still `pending` after an hour, 100 per run, first the R2 objects that no other row uses, then the rows. A task in the trash keeps its attachments. An accepted copy gets its own rows with the same `r2_key` (no bytes are copied), so an object only leaves R2 with its last row.

Every query on a per-person table filters on the `user_id` of the logged-in account (or of the key); an id of another account behaves like an id that does not exist, **unless the task is shared with you and you accepted** (`src/access.ts`: owner, or an accepted `task_shares` row on `COALESCE(parent_id, id)`). The owner of a task stays `tasks.user_id`, also for subtasks a participant adds; `tasks.list` and `tasks.position` are the owner's, a participant's are in their `task_shares` row (`overlay`). Writes on subtasks filter on the task's `user_id`, not on the requester. A participant may do everything except invite others; a shared top-level task cannot become a subtask (400 `err.share_is_shared`), and a task can only go under a parent with the same owner. There is no separate `due_at`: the reminder is also the deadline.

## Copy groups
Design: [docs/superpowers/specs/2026-10-18-kopie-voortgang-design.md](docs/superpowers/specs/2026-10-18-kopie-voortgang-design.md). (The sharing design still says a copy is fully separate; this one replaces that part.)
- **Column:** `tasks.copy_group` (migration `0011`, partial index), only on top-level tasks, `NULL` = no group. There is no group table: the members are the top-level tasks outside the trash with the same `copy_group`, and the owner of each is the person. Copies from before the migration stay separate. A copy in the trash does not count (and counts again after restoring); deleting the original leaves the others linked. Export leaves the column out, and a restore does not touch it.
- **Forming a group:** accepting a copy gives the original a new uuid if it has none yet (`WHERE copy_group IS NULL`, so two accepts at the same time end up in one group) and the new task the same value, in the same batch. A copy of a copy joins the same group. One copy per person per group: `POST /api/shares` (both modes) and accepting refuse with 409 `err.copy_exists` when the recipient already owns a task in the group.
- **`copies` in `GET /api/tasks`:** on a top-level task `{ members: [{ name, done, done_at, progress }], pending: [{ name }], self: { done, total } }`, or `null` without other members and pending invitations. `members` are the other copies (sorted by name; a shared copy counts once, with its owner's name, and its participants see the same members), never a copy of the viewer: a participant of a shared copy who also has a copy of their own does not see themselves. `self` counts the non-deleted subtasks of the task itself (checked and total, without the lines in the description), so the app knows its own progress even when the checked subtasks are not loaded. `progress` is the checked share (0–1) of the subtasks plus the `- [ ]` lines in the description (`countTasks` from `public/markdown.js`, so a line in a code block does not count), or `null` when there is nothing to count. For repeating copies `done` means a round further than the viewer's copy (`repeat_at` more than 2 hours later, so owners in time zones that switch daylight saving time on different days do not look done), with `done_at: null`. `pending` (open copy invitations) only goes to the owner. Never the title, description, subtasks or anything else of another person's copy. One extra query, only when a task in the answer has a group or a pending copy invitation.
- **In the app** (`public/copies.js`): a pill per other member in the meta line (done: green "Name ✓"; busy: the name with a small bar, no bar for `progress: null`) and a Copies block in the detail panel with the others, yourself and pending invitations. Your own bar counts the description as the client knows it, plus the subtasks: the total from `self`, the open ones from the local list (with the outbox applied), so a subtask checked locally counts at once, also offline; one added or deleted locally only counts after the next load. Never numbers like "3/7", only a bar or ✓; the label for screen readers is in words, rounded to a quarter. The bar's width is a CSS variable set from JS (the CSP blocks style attributes, not CSSOM).
- **Push when done:** when a top-level task in a group really goes from open to done (`setDone` changed a row, so `PATCH`, `/done`, the notification button and the widget all count, and two at once give one push), or a repeating copy rolls on, the owners of the other copies and their accepted participants get `copy.push_done` ("{name} is done ✓", name = who checked it) with the title of their own copy, in their own language, through `waitUntil`; no subscription means their fallback webhook. Nobody on the checked copy, no copy in the trash, nothing for unchecking or subtasks. Checking it again later sends again. The payload has no `taskId` but `url: /?task=<id>` of the recipient's own copy (`swclick.js` opens that task, also in an open window), `actions: []` (no Done/+1h buttons) and `tag: copy-<group>`; `sw.js` sets `renotify` when there is a tag, so a new push in the same group still alerts.

## Times
Always stored in UTC. A time without a zone counts in the time zone of the person making the request, a bare date as that person's reminder time (09:00 by default) in that zone (`src/time.ts`). The web app and Android already send UTC. Zone and reminder time come from that person's settings (D1, then `TIMEZONE`, then the built-in default), see "Settings".

The Worker passes the zone with every call: `Zone = { timeZone, reminderTime }` (`c.get('prefs')` fits) goes into `localToUtcIso`, `todayDefaultIso`, `repeatColumns`, `createTask`, `setDone` and `rollRepeat`. The calculation module `public/repeat.js` is shared with the PWA and has one module-global zone and default time; in the Worker only `inZone(z, fn)` (`src/time.ts`) sets them, runs `fn` synchronously and restores the previous values in `finally`. There is never an `await` inside, so two requests from people in different zones cannot see each other's zone. Nothing else in `src/` calls `setTimeZone` or `setDefaultTime` (`shiftWallClock` switches zones the same synchronous way).

## API
| Route | Purpose |
|---|---|
| `GET /.well-known/assetlinks.json` | Digital Asset Links, without login: the `handle_all_urls` statement for `ANDROID_PACKAGE` and the fingerprints in `ANDROID_CERT_SHA256`; `[]` when either is missing or no fingerprint is valid |
| Every `/api/tasks`, `/api/lists`, `/api/places` and `/api/inbox` route | Every query filters on `user_id` (the account of the session or key). An id that belongs to someone else behaves like an id that does not exist: 404, or 400 `err.parent_missing` as a `parent_id` |
| `GET /api/tasks` | Open tasks in order, your own plus those shared with you (with your list and order). `?done=1&limit=&offset=` for completed tasks, `?deleted=1&limit=&offset=` for the trash (newest first; a subtask deleted together with its parent belongs to the parent). `?q=` searches title and description (max. 200 characters). Every task has `share`: `null`, or on a top-level task `{ owner: {id, name}, mine, members: [{share_id, user_id, name, status}] }` (a pending copy is not a member). Every top-level task also has `copies` (see "Copy groups"); subtasks and the trash always `null` |
| `POST /api/tasks` | Create a task, optionally with `repeat`. Optional `id` (UUID from the client); an existing id returns the existing task (200), so resending is safe. An id that belongs to another account gives a 409 (`err.id_taken`) and changes nothing |
| `PATCH /api/tasks/:id` | Change fields, including `position` (drag), `pinned` (boolean; 400 `err.only_parents_pin` on a subtask) and `done`. `repeat` (RRULE or `null`); `occurrence` (ISO) next to `done`: the server only moves on or restores when it equals `repeat_at` |
| `DELETE /api/tasks/:id` | To the trash, including subtasks; for a shared task for everyone. 404 when you have no access (or it does not exist, or is already in the trash); the outbox drops a 404 silently. `?purge=1` (only on a task in the trash): the owner deletes it for good with its subtasks and share rows; a participant only removes it from their own trash (their share row goes) |
| `POST /api/tasks/:id/restore` | Out of the trash, with the subtasks deleted at the same time; a subtask whose parent is in the trash brings the parent back too. A reminder that passed meanwhile counts as notified |
| `POST /api/trash/empty` | Deletes for good all tasks in the trash **that you own**. Answer `{ deleted }` |
| `POST /api/shares` | `{ task_id, to, mode }`: invite someone (only the owner, 403 `err.share_owner_only`; only a top-level task, 400 `err.share_subtask`). `to` is an email address or an account name (case-insensitive): 404 `err.share_user_unknown`, 409 `err.share_user_ambiguous`, 400 `err.share_self`, 409 `err.share_exists`, 409 `err.copy_exists` (the recipient already has a copy in the task's copy group, for either mode); another `mode` gives 400 `err.share_mode`. Sends a push with Accept/Decline to the recipient (no subscription: their fallback webhook). Answer `201` with the row |
| `GET /api/shares/people` | The other accounts on this installation, `[{ id, name }]` (no email), for the picker in the share dialog. `POST /api/shares` also takes `to_user` (an id from this list) instead of `to`; an unknown id gives 404 `err.share_user_unknown` |
| `GET /api/shares/incoming` | Your pending invitations: `[{ id, mode, created_at, from: {name}, task: {title, description, remind_at, subtasks} }]` (not for tasks in the trash) |
| `POST /api/shares/:id/accept`, `/decline` | Accept: `shared` puts the task in your Inbox at the top of your order; `copy` makes your own tasks with new ids (as the original is now, subtasks all open, `source: 'share'`) and removes the row; the original and the new task end up in the same copy group (see "Copy groups"). A task in the trash or gone gives 410 `err.share_gone`; already having a copy in the group gives 409 `err.copy_exists`. Decline removes the row. Not yours or already handled: 404 |
| `DELETE /api/shares/:id` | The recipient stops sharing, or the owner removes someone or withdraws an invitation. For anyone else 404 |
| `attachments` in `GET /api/tasks` (and every other task answer) | `[{id, name, mime, size, width, height, created_at}]`, only `ready` ones, in upload order; always `[]` without `FILES` and in the trash view |
| `GET`/`POST /api/tasks/:id/attachments` | List, or add one: the body is the file itself (no multipart, streamed to R2), `?name=` the file name, `Content-Type` the type, `?w=&h=` the size of an image. Everyone with access to the task (owner or accepted participant) may add. A missing `Content-Length` gives 411 `err.length_required`, more than `MAX_UPLOAD_MB` (default 10) 413 `err.file_too_big`, more than 20 per task 400 `err.too_many_files`. Answer `201` with the metadata. Without `FILES` both routes give 404 |
| `GET /api/attachments/:id` | The file, after the access check on its task. JPEG, PNG, WebP, GIF and AVIF come inline with their own type; everything else (also SVG and HTML) as `application/octet-stream` with `Content-Disposition: attachment`, and `?download=1` always downloads. `Cache-Control: private, max-age=31536000, immutable` (an attachment never changes), `ETag`/`If-None-Match` (304) and one `Range` (206) |
| `DELETE /api/attachments/:id` | Removes the row; the R2 object goes when no other row (a copy) uses it. No access: 404 |
| `POST /api/tasks/:id/done`, `/reopen` | Complete and undo (Android), like PATCH `done` including subtasks. `/done` moves a repeating task on (it stays open); `/reopen` undoes the last step, within 15 minutes |
| `POST /api/tasks/:id/tomorrow` | Move the reminder to tomorrow at the owner's reminder time, in the owner's zone. For a repeating task only this occurrence |
| `POST /api/tasks/:id/snooze` | Move the reminder, 60 minutes by default, limited to 1 minute up to 30 days. For a repeating task only this occurrence |

## Security
- **Sessions:** the cookie is `exp.userId.version.hmac`. The version must equal that user's `users.session_version`; raising it logs out all of that user's sessions, nobody else's. Old cookies without a user (`exp.version.hmac`) are invalid, so everyone logs in once after the update. Every request carries a `userId`: from the session, from `api_keys.user_id` for a key, and the administrator for `API_TOKEN`, `INBOX_TOKEN` and `DEV_AUTH_BYPASS`. A key or cookie whose user no longer exists gets a 401. `users.last_seen` is updated at most once an hour. A cookie lives 30 days; with less than 15 days left the response carries a fresh one (sliding renewal). "Log out on other devices" raises the version and gives this device a fresh cookie.
- **Password:** stored per user as PBKDF2-SHA-256 with a salt in `users.password_hash` (100,000 iterations, the maximum in Workers). When it is set only it counts; without it the administrator can use `LOGIN_PASSWORD`, and a member cannot log in. **Emergency route** when the administrator forgot the password: `UPDATE users SET password_hash = NULL WHERE role = 'admin'`, and `LOGIN_PASSWORD` counts again, with an empty email address (or the administrator's address if one was set; command in [SETUP.md](SETUP.md)).
- **Keys:** `tick_` plus 32 random bytes as base64url, shown once. Only the SHA-256 is stored; a fast hash is enough for a random 256-bit value. `authorize()` looks in `api_keys` first (only for bearers starting with `tick_`), then at the old `API_TOKEN` and `INBOX_TOKEN` unless they are switched off in the app. A secret cannot be deleted from the app; `npx wrangler secret delete API_TOKEN` removes it for good. Revoking a key deletes the row and works at once.
- **Administrator only:** all `/api/users` routes need a session (or the dev bypass) of an account with the `admin` role (`adminOnly` in `src/guards.ts`). A member, and any bearer key (even `API_TOKEN`), gets a 403. Invitation and reset links are one-time and store only the SHA-256 of the code; consuming one is a single `UPDATE … RETURNING` (`src/links.ts`).
- **Session only:** all `/api/settings`, `/api/keys`, `/api/account`, `/api/devices`, `/api/export` and `/api/import` routes need a session (or the local dev bypass). A bearer key, even a `full` one, gets a 403, so a leaked phone or automation key cannot change the password, make keys or redirect the webhook. The one exception is `POST /api/device`, which only accepts a full key (or the `API_TOKEN` secret).
- **Rate limit:** `POST /login` first goes through the Workers Rate Limiting binding `LOGIN_LIMITER` (5 per 60 seconds, key `cf-connecting-ip`). It counts per Cloudflare location rather than globally, which is plenty against brute force on one password. A wrong attempt also waits 1.5 seconds.
- **Rate limit on the links:** `GET` and `POST` on `/invite/:code` and `/reset/:code` first go through `LOGIN_LIMITER` with key `link:<ip>` (5 per 60 seconds), so codes cannot be guessed. Only the hash of a code is stored and using it is one statement.
- **Headers:** a middleware sets `Content-Security-Policy` (`default-src 'self'`, no inline scripts or styles), `X-Content-Type-Options: nosniff`, `Referrer-Policy: same-origin` and a restrictive `Permissions-Policy` on every response. `img-src` also allows `https://tile.openstreetmap.org` for the map; `geolocation=(self)` is for the "my location" button.
- **Geocode limit:** `GET /api/geocode` goes through `GEOCODE_LIMITER` (10 per 60 seconds, one shared key). The Worker sends its own `User-Agent` with your URL and `ADMIN_CONTACT`, as Nominatim's usage policy asks. The app only searches on Enter.
- **Attachments:** a file is only served to someone with access to its task, never with a type the browser could run (only the five image types inline, the rest as a download), and with `Content-Security-Policy: sandbox` on top of the normal policy (the middleware adds a route's own CSP instead of replacing it), plus `nosniff`. Names lose their path and control characters. A bearer `inbox` key cannot reach the routes (the inbox rule).
- **MCP:** `/mcp` only accepts a `full` key (or the local dev bypass); a session cookie and an `inbox` key get a 403, so a browser page cannot drive it with your cookie. A request with an `Origin` other than the site itself gets a 403 (DNS rebinding). Through the tools a key reaches only task and list routes, not `/api/settings`, `/api/keys` or accounts (those are session-only anyway).
- **`DEV_AUTH_BYPASS`** only works on `localhost` and `127.0.0.1`.
- Without `SESSION_SECRET`, or without any password (none set in the app and no `LOGIN_PASSWORD`), nobody can log in (fail closed).

## Language
`public/i18n.js` holds every visible text in `en` and `nl` (a test checks both have the same keys). The Worker translates error messages in `onError`: an `HttpError` carries a key and variables, not text. The shell (`/`) is translated on the server with `HTMLRewriter` (`data-i18n` and `data-i18n-attr` attributes), so the service worker caches the translated page; the Worker drops the ETag of the untranslated file so a browser never gets a stale 304. The manifest is adjusted the same way. Notification buttons come translated in the push payload, because the service worker does not know the language.

The language is chosen **per device**: Automatic (the first of `navigator.languages` that is `en` or `nl`), English or Dutch. The PWA keeps the choice in `localStorage` and in the cookie `tick_lang` (`en` | `nl`; no cookie = automatic), so the server uses the same language for the shell, `/config.js`, the manifest, error messages and the login page. Server order: cookie, then `Accept-Language`, then the default language of the installation (see "Settings"). Push notifications are made by the server without a browser, so each subscription stores its `locale`; the fallback webhook uses the default language.

- **Modules** in `public/`: `db.js` (IndexedDB: local copy and outbox), `api.js` (fetch), `store.js` (state, changes, sync, all list logic), `render.js` (task list), `sidebar.js` (sidebar and drawer), `detail.js` (detail panel and task screen), `editor.js` (markdown editor), `markdown.js` (renderer), `lists.js` (list names), `listpicker.js`, `listmenu.js`, `popover.js` (pickers: below the button, or a bottom sheet on a narrow screen), `icons.js` (the line icons), `dialog.js`, `push.js`, `repeat.js` (repeat engine), `repeatpicker.js`, `i18n.js`, `settings.js` (config and language), `theme.js` (display preferences, loaded in `<head>`), `settingsview.js` (the settings page), `calendar.js` (calendar maths) and `calendarview.js` (the calendar page), `trash.js` (the trash view), `share.js` (share dialog, participants, invitation bar), `copies.js` (copy-group pills and the Copies block), `attachments.js` (the Attachments block, scaling photos down, the upload with progress, the large view) and `app.js` (start and events). Sharing, the trash and attachments only work online (the Add button is disabled offline; images already seen come from the browser cache); shared tasks are ordinary tasks in the local copy and outbox. Map: `map.js` and `places.js`.
- **App shell:** `sw.js` caches the page, all modules (the `SHELL` list, `settingsview.js`, `theme.js`, `androidapp.js`, `applink.js`, `swclick.js` and `next.js` included; when you change it, bump `CACHE`), the CSS, SortableJS, Leaflet, the manifest and the icons. Network first with a 4-second timeout: online you always get the newest version, so old and new modules never mix after a deploy; offline you get the last saved one. Only `res.ok && !res.redirected` goes into the cache, so never a redirect to `/login`. `/api/*` and the login do not go through the cache.
- **Local data:** after every successful `GET /api/tasks` the list is stored in IndexedDB. On start the app shows that copy first and then refreshes from the network.
- **Cache per user:** the local copy belongs to one account (`kv` key `owner`). On start `init(CONFIG.userId)` calls `ensureOwner`: when `owner` is another account, or missing (a cache from before accounts), it first clears `kv`, the outbox and the settings cache (`tick.settings-cache` in `localStorage`), so a shared browser never shows the previous person's tasks, not even briefly. When there was a previous owner and it is another account, it also unsubscribes this browser's push subscription (with a 2-second time-out, errors swallowed), because a session can end without the Log out button (expired cookie, logged out elsewhere, a reset or invitation link); the push service then answers 410 and the server removes the old row on the next send. Without a previous owner (a cache from before accounts) it leaves push alone, so browsers keep their notifications after the update. When the check fails, new changes are applied on screen but not written to the outbox. `sync`, `load` and the outbox wait for that check; if it fails, the app shows no local copy and replays no outbox (fail closed) and only uses what the server gives. Logging out (Settings › Account) first unsubscribes push in this browser (`DELETE /api/push/subscribe`; the browser subscription is removed even when that call fails), then posts `/logout`, then clears the same local data. After logging out, logging in, or signing up through an invitation or reset link, `forgetCachedConfig` (`public/next.js`) removes `/config.js` from every Cache Storage cache, so a slow network can never serve the previous person's `userId` from the cache.
- **Outbox:** every change is applied locally at once, put in the outbox and sent to the server in order. When that fails it waits; replay happens on `online`, on `visibilitychange`, on start and after every new change. Snoozing becomes a `PATCH remind_at` with an absolute time. A 404 during replay drops the change silently, another 4xx drops it with a message, a 5xx or 401 keeps waiting. Conflicts: last write wins per field.
- **Settings page offline:** it opens offline. The per-device parts (display, language, notifications) work as usual; the per-installation parts show the last known value, disabled, with "Can only be changed while online".
- **Client IDs:** new tasks get their id from the client (`crypto.randomUUID()`), so tasks and subtasks created offline can refer to each other.

The description is markdown, rendered by `markdown.js`, a line-by-line parser. Supported: headings `#` to `###`, paragraphs, bold, italics, strikethrough, inline code and code blocks, bullet and numbered lists (one level of nesting), checklists `- [ ]`/`- [x]` (clickable in the read view), quotes, links and bare `https://` addresses, and `---`. ## Lists
A list is the `list` column of tasks; the table `lists` (per person) only keeps lists you created, so a new empty list survives a reload and shows on every device. Rename and delete update that row too. **Inbox** is always on top after All and cannot be renamed or deleted. The list menu (right-click, "⋯", long press on mobile) offers Rename, Merge with… and Delete…; a name that already exists asks to merge. On desktop you can drag a task onto a list in the sidebar.

## Repeating reminders
A top-level task with a reminder can repeat daily, weekly, monthly or yearly. Completing it moves the same task on to the next occurrence.
- **Storage:** `repeat_rule` (an RRULE subset: `FREQ`, `INTERVAL` 1-99, `BYDAY` (with a rank for months, e.g. `3SU`/`-1SU`), `BYMONTHDAY`), `repeat_start` (time of day and phase of "every 2 weeks"), `repeat_at` (the occurrence the task is on now) and `repeat_prev` (internal JSON for undo). The API shows `repeat: {rule, start, at}` or `null`.
- **Completing** moves on to the first occurrence after both now and `repeat_at` (missed ones lapse; subtasks reopen). The PWA sends `occurrence`, so a repeated request from the outbox does nothing. **Undo** within 15 minutes restores the last step.
- **This time only:** snoozing or another date in the picker only moves `remind_at`. Clearing the reminder or making the task a subtask removes the rule.
- **Time:** all calculations use the wall clock of the owner's time zone (see "Times"), so 10:00 stays 10:00 across daylight saving changes. "On the 31st" falls on the last day of a short month.

## Search
Open tasks are filtered in the browser (title and description, case-insensitive); a matching subtask shows its parent. Completed tasks are searched on the server (`LIKE`, with `%` and `_` literal). `/` focuses the search field, Escape clears it.

## Location reminders (Android)
A task can have a place where Android alerts you: one notification on arrival (default) or on leaving.
- **PWA:** the Location pill opens a full-screen map: search, a pin in the middle, "my location", favourites, arrival or leaving, and a radius of 200 m to 2 km. Until you move the radius yourself it follows the trigger (200 m when leaving, 500 m on arrival); a favourite brings its own radius. The place is named after the chosen favourite, else the search result, else "Pinned place"; "Save as favorite" opens a name field in the panel. On a wide screen the controls sit in a panel to the right of the map. Leaflet loads on first use; tiles are not cached.
- **Android:** after every successful refresh the app registers geofences for open tasks with a place that has not fired yet (at most 100, Android's limit), only when the set changed. On a geofence event it checks the task with the server (falling back to its cache), shows "📍 Arrived at X" or "📍 Left X" with a Complete action, and sends `PATCH location_notified = true`. The decision logic is plain Java with JUnit tests (`NotifyDecision`, `GeoPlan`).
- **From the PWA to the phone:** after a place change the PWA opens an intent link `tick://sync?...` (only with `ANDROID_PACKAGE` set), so the app syncs within about a minute. A place set on a laptop arrives through a periodic job, within about 15 minutes.

## In the app (TWA)
The Android app opens the PWA at `/?app=android` (plus `&pair=1` while it has no API key). `initAndroidApp` in `public/androidapp.js` remembers the app in `sessionStorage` (`tick.app`) and removes both parameters from the address bar. With `pair=1` and `ANDROID_PACKAGE` set it calls `POST /api/pair` and hands the one-time code to the app through an intent link (`intent://pair?code=…`, built in `public/applink.js`, which has no imports so the tests can load it). It polls `GET /api/pair/:id` every second; after 3 seconds without `used` it shows a bar with an "Open the Tick app" button, and after 2 minutes the code expires. Once the code is used it switches on web push (errors are swallowed; the switch in Settings is the fallback). When the app and another Android browser both have push on, a hint offers Settings › Devices (once, `tick.dupHint` in `localStorage`). Settings › Devices gets a "Phone settings" button (`intent://settings…`) in the app. After logging in or signing up inside the app (`sessionStorage` `tick.app` is `android`, or the referrer starts with `android-app://`), `afterLogin` in `public/next.js` adds `app=android&pair=1` to the target (and checks the result with `safeNext` again, because the URL parser can turn `/.//host` into `//host`), so the app pairs again with a key of whoever is now logged in, even if it already had a key. A tap on a notification is decided by `public/swclick.js` (a classic script that `sw.js` loads with `importScripts`): no window open gives `/?task=<id>` (or the payload's `url`), an open window gets `postMessage({ type: 'open-task', id })` with `taskId` or the `task` from the payload's `url`, which `app.js` handles like `?task=`.

On the phone: `PairActivity` (transparent) handles `tick://pair?code=…` (`PairLink` reads the code), trades it on a background thread through `POST /api/pair/redeem` (no `Authorization`, name `Build.MODEL`, and the key it already has as `old_key`, so the server revokes it), stores the key and the `user_id` from the answer (`Prefs.userId`), wipes the local data (cache, pending, location state, geofences; `Prefs.wipeAccountData`) when that `user_id` differs from the stored one (`CacheWipe`; a key from before 1.4 has none, so pairing with a known `user_id` wipes too), also wipes after a 401 and when a different key is typed by hand in `MainActivity`, syncs, reports the device status, asks for notification permission on Android 13+ and closes, so the TWA is back. On failure it shows a toast and the PWA's own button remains. `MainActivity` is "Tick on this phone" (`tick://settings`, and the "Phone settings" shortcut next to "New task"): link status with an "Open Tick" button, location notifications, widget settings, and the key field collapsed under "Advanced". Taps on a widget task or a location notification go through `WidgetClickActivity` to `Launch.task`, which opens `/?app=android&task=<id>` in the TWA (Browser Helper accepts an intent URL with the same https origin as `DEFAULT_URL`). A 401 on any API call means the key was revoked: `Api.call` clears it and the widget shows "not linked", so the next start pairs again; 403 and 5xx keep the key.

Web push in the app: Browser Helper's `DelegationService` makes Chrome show the PWA's notifications as notifications of the app. The small icon is the site's `badge` (`/badge-96.png`); when Chrome cannot load it in time (for example a phone just out of Doze), it uses the service's `SMALL_ICON`. That has to be a bitmap (`ic_notify_bitmap`, PNGs per density from `scripts/make-icons.mjs`): Browser Helper hands Chrome a decoded bitmap, so with a vector drawable Chrome falls back to its own icon.

## Tests
Vitest with `@cloudflare/vitest-plugin`: the tests run in the Workers runtime against a local D1 with the same migrations as production (`test/`). They use your `wrangler.jsonc` when it exists and `wrangler.example.jsonc` otherwise; the bindings in `vitest.config.ts` fix `LOCALE` (`en`), `TIMEZONE` (`Europe/Amsterdam`) and the test secrets. Android has JUnit tests for the geofence logic, start URLs, pair links and when to forget the key. CI (`.github/workflows/ci.yml`) runs typecheck and tests on every push and pull request.

## Known limitations
- iPhone push only works when the PWA is on the home screen; `FALLBACK_WEBHOOK` can cover that.
- The cron runs every minute, so reminders can be up to a minute late.
- Offline only works after the app has been opened once online and logged in.
- Location notifications only work on Android. Android reports geofences with a delay of a few minutes. A small circle notifies sooner when leaving, but below 200 m the location drift indoors gives false alarms; on arrival, a car crosses a small circle in seconds. Hence 200 m as the minimum and the default when leaving, and 500 m by default on arrival.
- The map only works online.
- No initial trigger: if you are already at the place when you set it, the arrival notification only comes next time.
- Repeating reminders can have an end date (`UNTIL`), but no maximum count.
- Quick add in the Android app keeps its own 09:00 for a date without a time; it does not follow the reminder time setting.
- Another device keeps calculating in the old time zone or reminder time until it starts again (the server stays leading when it completes a repeating task).
- A phone on an Android app older than 1.2 does not report its notification and location status; the Devices block shows only "last seen".
- The old secrets (`API_TOKEN`, `INBOX_TOKEN`) can be switched off in the app but only removed with `wrangler secret delete`.
- Attachments are not in the backup file, only listed in it. Restoring a backup on another installation leaves them behind.
- A deleted attachment is gone at once; it has no trash. The Android widget does not show attachments.
